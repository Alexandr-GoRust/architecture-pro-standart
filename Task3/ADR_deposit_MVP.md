### Название задачи: MVP онлайн-открытия депозитов (интернет-банк и сайт)

### Автор: команда цифровой трансформации розничного бизнеса

### Дата: 20.10.2026

### Функциональные требования

| **№** | **Действующие лица или системы** | **Use Case** | **Описание** |
| :-: | :- | :- | :- |
| UC-1 | Клиент, интернет-банк, сервис интеграции депозитов, АБС | Просмотр депозитов и персональной ставки | Клиент открывает раздел «Депозиты» в интернет-банке. Заявка через сервис интеграции передаётся в систему кол-центра как обращение. Для идентификации клиент приходит в отделение (ограничение регулятора). |
| UC-7 | Оператор кол-центра, система кол-центра | Консультация по заявке с сайта | Оператор изучает обращение в системе кол-центра, звонит клиенту, рассказывает условия по актуальным ставкам и может предложить особые условия. |

### Нефункциональные требования

| **№** | **Требование** |
| :-: | :- |
| НФТ-1 | Новые сервисы доступны 99,9% времени и работают 24/7; запуск не менее чем в двух экземплярах (отказ экземпляра не останавливает онлайн-канал). |
| НФТ-2 | Отказоустойчивость онлайн-канала при сбое в ЦОД: резервный ЦОД, равномерное распределение нагрузки между серверами и ЦОД. |
| НФТ-3 | Отклик операций онлайн-канала — миллисекунды; справочные данные (включая ставки) кэшируются, устраняется текущая проблема загрузки справочников дольше секунды. |
| НФТ-4 | Новая онлайн-нагрузка не ложится напрямую на БД АБС: обращения к АБС только через сервис интеграции с кэшированием и ограничением частоты запросов (АБС масштабируется только вертикально). |
| НФТ-5 | Передача данных с сайта и из интернет-банка шифруется (TLS). |
| НФТ-6 | Доработки ядра интернет-банка силами подрядчика исключены; подтверждение по СМС реализуется силами банка. |
| НФТ-7 | Технологии — существующие или совместимые с платформами банка; наличие экспертизы (Java-стек — специалисты команды АБС). |
| НФТ-8 | Новый функционал изолирован от монолита интернет-банка (микросервисный подход в рамках задачи депозитов), совместимость с будущим внедрением Kafka. |
| НФТ-9 | Единый источник истины по ставкам — АБС; допустимая рассинхронизация с онлайн-каналами ограничена временем жизни кэша (TTL). |
| НФТ-10 | Разрабатывается документация на новые сервисы и интеграции для дальнейшего расширения. |

### Решение

Диаграммы: `C4_context_deposit_MVP.png` (контекст, L1) и `C4_containers_deposit_MVP.png` (контейнеры, L2; исходники `.puml` приложены рядом). На диаграмме контейнеров детализированы интернет-банк и АБС.

**Основная идея.** Онлайн-каналы не обращаются к АБС напрямую ни через БД (как сегодня), ни через API. Между ними вводится **сервис интеграции депозитов** — новое приложение команды АБС на Java Spring Boot с собственной схемой Oracle (кэш ставок, заявки, СМС-коды, лиды с сайта). В АБС появляются два новых элемента, которые делает команда АБС: **API депозитов** (REST-интерфейс: выдача ставок, приём заявок, статусы) и **справочник ставок с аудитом** (PL/SQL, единый источник истины вместо Excel).

**Логика принятия решений.**

1. **Почему сервис-посредник, а не прямая интеграция.** Прямой доступ к БД АБС (текущая практика) и прямой доступ интернет-банка к API АБС запрещены требованием НФТ-4: БД АБС перегружена и масштабируется только вертикально, а онлайн-канал требует 99,9% и миллисекундных откликов. Кэш ставок с TTL в сервисе интеграции даёт миллисекундный отклик на чтениях (НФТ-3) и резко ограничивает поток запросов к АБС.
2. **Почему Java Spring Boot + Oracle.** В команде АБС есть Java-специалисты (уже сопровождают систему кол-центра на этом стеке) — выполняются НФТ-7 и независимость от подрядчика (НФТ-6). Oracle уже лицензован и администрируется; для сервиса выделяется отдельная схема, не связанная с перегруженной БД ядра АБС.
3. **Почему новый функционал не в монолите интернет-банка.** Ядро обновляет подрядчик, доработки ядра исключены (НФТ-6, НФТ-8). В монолите делается только новая страница (UI) депозитов — такие изменения команда банка вносит самостоятельно; вся бизнес-логика — в сервисе интеграции. Сервис масштабируется горизонтально независимо от платформы (НФТ-1, НФТ-2) и не наследует несовместимость платформы с Kafka.
4. **Почему ставки ведутся в АБС.** Справочник ставок — мастер-данные депозитного домена, а процесс согласования ставки и обработки заявки в MVP остаётся в АБС, где работает бэк-офис. Разнесение ставок в отдельное хранилище создало бы второй источник истины и дублирование процесса согласования. Ролевая модель АБС сохраняет разграничение доступа бэк-офисов (UC-5), аудит закрывает регуляторный разбор инцидентов.
5. **СМС без доработки ядра интернет-банка.** Генерация кодов, проверка и отправка уведомлений — в сервисе интеграции; доставка через существующий СМС-шлюз телеком-оператора, который уже поддерживает IT-отдел (UC-2, UC-4, НФТ-6).
6. **Лиды с сайта.** Сайт принимает заявку (телефон, Ф. И. О.) и передаёт её в сервис интеграции по TLS (НФТ-5); сервис передаёт лид в систему кол-центра по REST — у платформы кол-центра есть возможности расширения, доработку выполняют Java-специалисты команды АБС или команда сопровождения подрядчика (UC-6, UC-7).

### Альтернативы

1. **Заявки из интернет-банка напрямую в БД АБС** (как сегодняшние платежи). Отклонено: усиливает текущую проблему — перегруженная БД АБС становится зависимостью онлайн-канала с требованием 99,9%; связность схем делает каждое изменение АБС опасным для интернет-банка; кэширования нет — миллисекундный отклик недостижим.
2. **Прямой доступ интернет-банка к API АБС без сервиса-посредника.** Отклонено: прямо запрещён НФТ-4/требованием ТЗ; связывает релизные циклы интернет-банка и АБС; нагрузка онлайн-канала без ограничений ложится на АБС.
3. **Функционал депозитов внутри монолита интернет-банка.** Отклонено: потребовал бы доработки ядра платформы подрядчиком (СМС-функционал ядра) — ТЗ прямо просит этого избежать; масштабирование монолита = масштабирование всей платформы в одном ЦОД; платформа несовместима с Kafka на перспективу.
4. **Мастер-справочник ставок в БД сервиса интеграции (вне АБС).** Отклонено: процесс согласования ставки в MVP остаётся в АБС — возникли бы два источника истины и двойной ввод; бэк-офис работает в АБС, перенос процесса — уже за рамками MVP (задача целевого состояния).
5. **СМС-подтверждение через ядро интернет-банка.** Отклонено: доработка ядра силами подрядчика, от которой ТЗ предписывает уйти; функция критична для безопасности операции и должна контролироваться банком.

**Недостатки, ограничения, риски**

- **Новая эксплуатируемая единица.** Сервис интеграции требует мониторинга, резервного копирования, регламента выкатки; команда АБС (20 человек) берёт дополнительную нагрузку — риск ресурсный.
- **Кэш ставок.** В пределах TTL онлайн-каналы могут показывать ставку, отличную от актуальной в АБС; окно рассинхронизации фиксируется в контракте API и отображается («ставка на такое-то время»). Риск минимален: ставки меняются редко и подконтрольны банку.
- **Первая REST-интеграция АБС.** Команда АБС не делала интерфейсных API — нужен прототип и нагрузочное тестирование API на стенде; рост числа онлайн-заявок всё равно добавляет нагрузку на обработку в АБС (ручная обработка MVP остаётся в АБС).
- **MVP не ускоряет согласование специальных ставок.** Обработка заявок бэк-офисом остаётся ручной; выигрыш MVP — в канале подачи и уведомлениях. Автоматизация полного процесса — цель второго этапа (целевое состояние через год).
- **Три точки изменения UI** (страница в монолите ИБ, страница сайта, API сервиса) при изменении продуктовой линейки — управляется документацией API (НФТ-10) и единым источником ставок.
- **Зависимость от подрядчика кол-центра** для приёма лидов: если доработку делает подрядчик — вписать в контракт; альтернатива — силами Java-специалистов команды АБС.
