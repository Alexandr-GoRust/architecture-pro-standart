### Название задачи: Передача актуальных ставок по депозитам в кол-центры (свой и партнёрский)

### Автор: команда цифровой трансформации розничного бизнеса

### Дата: 20.10.2026

### Функциональные требования

| **№** | **Действующие лица или системы** | **Use Case** | **Описание** |
| :-: | :- | :- | :- |
| UC-1 | Оператор кол-центра банка, клиент, система кол-центра | Консультация по актуальным ставкам | Клиент звонит в кол-центр. Оператор видит актуальные ставки по депозитам непосредственно в интерфейсе системы кол-центра (данные поступают по API из кэша сервиса интеграции депозитов, источник — справочник ставок в АБС). Оператор консультирует клиента и при необходимости заводит обращение по текущему процессу. |
| UC-2 | Оператор партнёрского кол-центра, клиент, система партнёрского кол-центра | Консультация по актуальным ставкам (партнёр) | Система партнёрского кол-центра периодически загружает со SFTP-сервера банка файл со ставками (а также при появлении нового файла). Оператор партнёра видит актуальные ставки в своей системе и консультирует клиентов по переданным банком скриптам. |
| UC-3 | Менеджер бэк-офиса, АБС, сервис интеграции депозитов | Изменение ставки и её распространение | Менеджер изменяет ставку в справочнике АБС. Сервис интеграции обновляет кэш (по событию изменения и по расписанию), после чего API отдаёт свежие ставки системе кол-центра, а модуль экспорта формирует и выкладывает на SFTP новый файл со ставками. |
| UC-4 | Сотрудник IT-отдела, SFTP-сервер | Администрирование файлового обмена | IT-отдел разворачивает SFTP-сервер, выдаёт партнёру доступ (только чтение из изолированного каталога), настраивает мониторинг выкладки файлов и алертинг при отсутствии свежего файла. |

### Нефункциональные требования

| **№** | **Требование** |
| :-: | :- |
| НФТ-1 | Актуальность ставок у операторов банка — не хуже времени жизни кэша (минуты); у партнёрского кол-центра — не более часа с момента изменения ставки. |
| НФТ-2 | Во внешнюю систему партнёра передаются только публичные ставки депозитов; персональные и специальные ставки клиентов, данные кредитного риска не передаются. |
| НФТ-3 | Обмен с партнёром — только по SFTP: шифрование канала, аутентификация по ключам, изолированный каталог (chroot), доступ только на чтение. API-доступ партнёру недоступен по условиям интеграции. |
| НФТ-4 | При недоступности API сервиса интеграции система кол-центра продолжает отображать последний успешно загруженный срез ставок (деградация вместо отказа) с пометкой времени среза. |
| НФТ-5 | Файл ставок содержит версию и дату формирования; целостность проверяется контрольной суммой; оператор партнёра видит актуальность среза. |
| НФТ-6 | API ставок наследует требования MVP: доступность 99,9%, работа 24/7, горизонтальное масштабирование (не менее двух экземпляров). |
| НФТ-7 | Решение строится на сервисе интеграции депозитов из ADR «MVP онлайн-депозитов» — новые компоненты, а не новая система. |

### Решение

Диаграммы: `C4_context_rates_callcenter.png` (контекст) и `C4_components_rates_callcenter.png` (компоненты; исходники `.puml` приложены рядом).

**Основная идея.** Единый источник истины по ставкам — справочник ставок в АБС (вводится в MVP онлайн-депозитов). Распространение ставок на кол-центры выполняет уже спроектированный сервис интеграции депозитов, в котором добавляются три компонента: **API ставок** (REST для системы кол-центра банка), **экспорт ставок в файл** (формирование CSV при изменении справочника и по расписанию) и **SFTP-клиент** (выкладка файла партнёру). Для партнёра IT-отдел разворачивает **SFTP-сервер** в контуре банка с изолированным каталогом и доступом только на чтение.

**Логика принятия решений.**

1. **Свой кол-центр — API, партнёрский — файлы.** Система кол-центра банка — микросервисная платформа (Java Spring Boot) с возможностями расширения и уже развёрнута в контуре банка: для неё естественен REST API с кэшированием среза на стороне кол-центра (НФТ-4, НФТ-6). Система партнёрского кол-центра — внешняя, по условиям партнёра доступны только файлы (SFTP), API-вызовы невозможны.
2. **Почему распространение ставок — в сервисе интеграции, а не в АБС.** Кэш ставок и синхронизация с АБС уже есть в сервисе; экспорт и API — переиспользование того же кэша (НФТ-7). Выдача ставок внешним потребителям из АБС добавила бы нагрузку на перегруженную БД и потребовала бы от команды кол-центра интеграции с legacy-интерфейсами.
3. **Почему файл формируется при изменении и по расписанию.** Изменения ставок редки, но гарантию свежести для партнёра даёт только дублирование канала: событийная выкладка при изменении справочника плюс контрольная выкладка по расписанию (НФТ-1); отсутствие свежего файла отслеживается мониторингом (UC-4).
4. **Безопасность файлового канала.** Передаются только публичные ставки (НФТ-2), канал шифруется, партнёр аутентифицируется ключом и ограничен chroot-каталогом с правом только чтения (НФТ-3). Версия и контрольная сумма файла защищают от чтения повреждённого или устаревшего среза (НФТ-5).

### Альтернативы

1. **Интеграция системы кол-центра напрямую с API АБС.** Отклонено: нагрузка на перегруженную БД АБС; для команды сопровождения кол-центра это самая сложная точка интеграции; дублирование кэширования, которое уже делает сервис интеграции.
2. **Файловый обмен через SFTP и для своего кол-центра.** Отклонено: у платформы кол-центра есть REST-возможности; файлы — шаг назад (задержка, ручные действия, нет пометки среза в момент консультации).
3. **Передача ставок партнёру по электронной почте (как сегодняшние Excel).** Отклонено: ручной канал без SLA, шифрование и контроль доставки не гарантируются, рассылка вовне — риск утечки; SFTP закрывает то же потребность штатными средствами.
4. **Отдельный сервис публикации ставок.** Отклонено: дублирование кэша, синхронизации и инфраструктуры; задача закрывается компонентами существующего сервиса интеграции (НФТ-7).

**Недостатки, ограничения, риски**

- Свежесть ставок у партнёра зависит от дисциплины загрузки его системой: ограничиваемся договорным SLA и пометкой версии среза в интерфейсе оператора партнёра.
- Доработка UI системы кол-центра зависит от подрядчика платформы (или Java-специалистов команды АБС) — риск сроков; задача в роадмапе выделена отдельной дорожкой.
- SFTP-сервер — новая эксплуатируемая единица: нужны мониторинг, бэкап, регламент управления ключами партнёра.
- Формат файла и SLA обновления необходимо зафиксировать договором с партнёром до запуска.
- При длительной недоступности SFTP ставки у партнёра устаревают — алертинг IT-отделу (UC-4) обязателен.
- Кэш-срез в системе кол-центра при недоступности API может отставать от АБС — оператору показывается время среза (НФТ-4).
