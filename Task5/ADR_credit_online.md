### Название задачи: Заявка на кредит онлайн (сайт и интернет-банк, с предодобренными предложениями)

### Автор: команда цифровой трансформации розничного бизнеса

### Дата: 20.10.2026

### Функциональные требования

| **№** | **Действующие лица или системы** | **Use Case** | **Описание** |
| :-: | :- | :- | :- |
| UC-1 | Потенциальный клиент, сайт, сервис кредитных заявок, кредитный конвейер | Заявка на кредит с сайта без паспорта | Клиент видит на сайте предложение открыть кредит (полные условия — из кредитного конвейера). Оставляет телефон и Ф. И. О. — заявка создаётся в конвейере напрямую через API; клиенту приходит СМС-приглашение прийти в отделение для идентификации и продолжения оформления. |
| UC-2 | Потенциальный клиент, сайт, конвейер, скоринг, БКИ, СМС-шлюз | Заявка с паспортом — мгновенное решение | Если клиент дополнительно заполняет паспортные данные, конвейер сразу запускает скоринг. Клиент новый, поэтому скоринг использует только общие данные бюро кредитных историй (запрос онлайн по REST). По оценке конвейер формирует предварительное решение (одобрение/неодобрение); клиент получает СМС о статусе и приглашение в отделение для получения кредита и идентификации. |
| UC-3 | Клиент, интернет-банк, сервис кредитных заявок, конвейер, скоринг | Заявка по предодобренному предложению | Клиент видит в интернет-банке список кредитов с актуальными условиями и предодобренное предложение (сумма рассчитана по ранее выполненному скорингу и платёжной дисциплине). Указывает счёт зачисления и данные заявки, подтверждает операцию СМС-кодом. Заявка попадает в конвейер напрямую; при изменении ситуации выполняется повторный скоринг по упрощённой процедуре; сотрудник обрабатывает заявку в тот же рабочий день. |
| UC-4 | Менеджер отделения, АБС, конвейер | Продолжение онлайн-заявки в отделении | Клиент с предодобрением приходит в отделение. Менеджер находит по клиенту (телефон, паспортные данные) ранее созданную онлайн-заявку: АБС запрашивает её через API конвейера и продолжает работу с той же заявкой. Для полностью нового клиента без онлайн-заявки менеджер создаёт заявку в АБС по существующему процессу. |
| UC-5 | Менеджер бэк-офиса кредитов, конвейер | Обработка онлайн-заявок | Онлайн-заявки появляются в рабочем списке конвейера сразу после подачи (прямой API, минуя суточный обмен с АБС). Менеджер рассматривает заявку с учётом оценки скоринга и фиксирует решение; заявки по предодобрениям приоритезируются и завершаются в течение рабочего дня. |
| UC-6 | Клиент, конвейер, сервис кредитных заявок, СМС-шлюз | Уведомление о смене статуса | При каждом изменении статуса заявки конвейер передаёт событие сервису кредитных заявок (callback), тот отправляет клиенту СМС через существующий СМС-шлюз телеком-оператора. |

### Нефункциональные требования

| **№** | **Требование** |
| :-: | :- |
| НФТ-1 | Решение по заявке с достаточными данными — не позднее одного дня; по заявкам с предодобренными предложениями — в течение того же рабочего дня. |
| НФТ-2 | Онлайн-заявки передаются в кредитный конвейер напрямую через API: обмен АБС ↔ конвейер «раз в сутки по БД» ускорить невозможно, поэтому новый процесс его не использует. |
| НФТ-3 | Кредитный конвейер и система скоринга уже поддерживают горизонтальное масштабирование и работу 24/7 — новая онлайн-нагрузка принимается без изменения их инфраструктуры. |
| НФТ-4 | Скоринг не нагружается предрасчётами: предодобренные предложения формируются только на основе уже выполненных скорингов и имеющейся платёжной дисциплины. |
| НФТ-5 | Передача данных с сайта и из интернет-банка шифруется (TLS); паспортные данные передаются и хранятся с минимизацией доступа. |
| НФТ-6 | Новый сервис кредитных заявок доступен 99,9%, работает 24/7, запускается не менее чем в двух экземплярах. |
| НФТ-7 | Технологии сервиса — Java Spring Boot и Oracle (существующая экспертиза команды АБС), паттерн повторяет сервис интеграции депозитов из MVP. |
| НФТ-8 | Клиентские СМС (коды подтверждения и уведомления о статусах) отправляются через существующий СМС-шлюз телеком-оператора из единой точки — сервиса кредитных заявок. |
| НФТ-9 | Выдача (зачисление) кредитных средств остаётся в существующем суточном цикле конвейер → АБС; SLA «решение за один день» относится к решению, зачисление — до суток после него. |

### Решение

Диаграммы: `C4_context_credit_online.png` (контекст, L1) и `C4_components_credit_online.png` (компоненты, L2; исходники `.puml` приложены рядом). Детализированы новый сервис кредитных заявок и кредитный конвейер.

**Основная идея.** Вводится **сервис кредитных заявок** (Java Spring Boot, схема Oracle для СМС-кодов и журнала уведомлений; команда АБС) — единая точка входа для сайта и интернет-банка. В кредитном конвейере появляются **REST API конвейера** (приём онлайн-заявок напрямую, каталог условий, предодобренные предложения, события статусов) и **модуль предодобренных предложений**. Онлайн-заявки идут в конвейер напрямую и не используют суточный обмен с АБС. Скоринг и БКИ не изменяются. АБС получает одну доработку — поиск онлайн-заявки клиента для продолжения в отделении.

**Логика принятия решений.**

1. **Почему прямой канал онлайн → конвейер, минуя АБС.** Требование НФТ-1 («тот же рабочий день») несовместимо с суточным пакетным обменом АБС ↔ конвейер, который ускорить невозможно (НФТ-2). Конвейер уже горизонтально масштабируем и работает 24/7 (НФТ-3) — он и становится точкой приёма онлайн-заявок, как и предписывает ТЗ. АБС подключается на концах процесса: поиск заявки для отделения (через API) и зачисление средств (существующий суточный канал, НФТ-9).
2. **Почему нужен сервис кредитных заявок, а не интеграция каналов напрямую с конвейером.** Коробочный конвейер не должен знать особенности клиентских каналов; СМС-коды подтверждения, TLS-терминация, лимиты и журналирование уведомлений сосредотачиваются в одном сервисе (НФТ-5, НФТ-8). Паттерн повторяет сервис интеграции депозитов — единый стиль, переиспользование экспертизы и документации (НФТ-7).
3. **Предодобренные предложения — в конвейере, из уже выполненных скорингов.** Оценки скорингов и привязка платежей к договорам уже хранятся в БД конвейера; предложения формируются фоновым заданием из этих данных без единого вызова скоринга (НФТ-4). Интернет-банк показывает их через сервис заявок.
4. **Повторный скоринг — упрощённый, при подаче заявки.** Конвейер вызывает скоринг онлайн только в момент рассмотрения конкретной заявки (как сегодня), по предодобренным — по упрощённой процедуре; это штатный сценарий скоринга, а не предрасчёт (НФТ-4).
5. **Мгновенное решение на сайте.** Для нового клиента с паспортом конвейер выполняет скоринг только по данным БКИ (других источников нет) и принимает предварительное решение автоматически по бизнес-правилу; финальное оформление и идентификация — в отделении (регуляторное ограничение).
6. **Продолжение заявки в отделении.** АБС запрашивает конвейер по API о существующей заявке клиента (UC-4) — это единственная доработка АБС в данном решении; заявки, созданные в отделениях, продолжают идти по суточному каналу, как сегодня.
7. **СМС через единую точку.** Конвейер передаёт события статусов сервису заявок (callback), сервис отправляет все клиентские СМС через существующий шлюз (НФТ-8): единые тексты, контроль повторов, один договор со шлюзом.

### Альтернативы

1. **Онлайн-заявки через АБС по существующему суточному обмену.** Отклонено: заявка попала бы в конвейер лишь на следующий день — требование «решение в течение одного дня» невыполнимо принципиально.
2. **Участить обмен АБС ↔ конвейер.** Отклонено: ТЗ прямо фиксирует, что ускорить обмен между базами невозможно.
3. **Интеграция сайта и интернет-банка напрямую с API конвейера.** Отклонено: клиентские СМС-коды, шифрование и лимиты пришлось бы реализовывать в двух каналах и в коробочном конвейере; доработка коробки под клиентские каналы растёт в цене и зависит от подрядчика.
4. **Массовый предрасчёт скорингов для предодобренных предложений.** Отклонено: прямо запрещено ТЗ — скоринг нагружен в рабочие часы; предложения формируются из уже выполненных скорингов.
5. **Отдельный сервис предодобренных предложений.** Отклонено: все исходные данные (оценки скорингов, платежи, договоры) уже в БД конвейера; отдельный сервис дублировал бы их и добавил бы интеграцию.
6. **Отправка СМС о статусах напрямую из конвейера.** Отклонено: разбросала бы клиентские уведомления по двум системам; единая точка уведомлений (сервис заявок) уже умеет работать со СМС-шлюзом.

### Недостатки, ограничения, риски решения

- **Зачисление средств — до суток после решения** (суточный цикл конвейер → АБС). Ускорение потребует перестройки учёта в АБС — за рамками данного решения; фиксируется в клиентском SLA.
- **Заявки из отделений не ускоряются:** новые клиенты, оформляющие кредит только в отделении, по-прежнему попадают в конвейер раз в сутки. Их поток мал относительно онлайн-канала.
- **Качество мгновенного решения на сайте ограничено данными БКИ** (клиент новый): возможны отказы по формальным признакам; при визите в отделение решение уточняется по данным АБС.
- **Доработка коробочного конвейера (Camunda):** онлайн-маршрут, API и модуль предодобрений — риск зависимости от версии платформы и подрядчика, внедрявшего систему; mitigация — обработчики на Java уже умеет менять команда банка.
- **Три задействованные команды** (АБС, конвейер, подрядчик кол-центра не участвует, но сайт дорабатывается) — координация сроков через роадмап; запуск после MVP депозитов (второе полугодие).
- **Двойной канал приёма заявок** (онлайн → API конвейера; отделения → суточный обмен) — риск дублирования заявок для одного клиента; закрывается поиском существующей заявки по клиенту (UC-4) перед созданием новой.
- **Персональные данные (паспорт) через сайт:** минимизация хранения (в сервисе заявок не хранятся, передаются в конвейер по TLS), журналирование доступа.
